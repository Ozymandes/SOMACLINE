Somacline started as a question: what would a system monitor look like if it
didn't look like a dashboard? The answer turned out to be a piece of
scientific hardware that never existed, five mathematical organisms living
inside it, and your machine's actual telemetry — `/proc` and `/sys`, sampled
at 5 Hz — standing in for their physiology. Everything renders on the CPU,
and the whole thing is verified against a reference implementation to the
byte.

## What it is

Behind the observation glass lives a specimen: a point cloud generated by a
published generative equation, ported verbatim. At rest it reduces *exactly*
to its source — a parity gate asserts it. Then the instrument reads `/proc`
and `/sys`, and the specimen responds. CPU load becomes a ripple travelling
down the body. Thermal pressure breaks a mirror plane, or warms a pulse from
cyan toward amber. Memory pressure crowds the field.

The telemetry never edits the equation. Physiology acts on the solved cloud,
and every drive is proportional to its own channel, so a machine at rest
hands back the published creature — exactly, every frame. There is a gate in
the test suite that asserts this, because asserting things is cheaper than
believing them. Under load you are watching the same creature with a
physiology.

The console around it is manufactured from six generated hardware modules:
shell, header, observation chamber, telemetry rack, selector, status rail.
Everything that changes is drawn live, in code, into recesses measured off
the module — the seven-segment readouts, the sixty-second graphs, the lamps,
the engraved keys, the clock. **Nothing on the instrument is a baked
reading.**

## The organisms

The five specimens are the published generative sketches of
[@yuruyurau](https://x.com/yuruyurau) — the "one tweet" p5.js school, where a
handful of characters evaluates one closed-form expression tens of thousands
of times a frame. Each sketch is ported first to NumPy and then to Rust, with
the original reproduced verbatim beside the port in
[`rust/src/sources.rs`](rust/src/sources.rs).

## System behaviour

Somacline is meant to be left open. It is built to cost almost nothing while
you are not looking at it.

| state | what it does |
|---|---|
| focused | 60 FPS, ~15 % of one core |
| visible, unfocused | 30 FPS, ~10 % |
| covered by another window | stops, 0.25 % |
| on another workspace | stops, 0.12 % |

Telemetry is read at 5 Hz and only at 5 Hz — never at frame rate. Each graph
holds the last sixty seconds. When the compositor stops asking for frames, the
simulation stops with it, and on resume the elapsed time is clamped so nothing
teleports.

Three layouts resolve from the window size — COMPACT, INSTRUMENT, ARCHIVE —
and a resize rebuilds nothing. Fractional display scaling is gated at 1.0,
1.25, 1.5, 1.6, 1.75 and 2.0.

## Architecture

```
  telemetry  /proc, /sys, 5 Hz ──▶ physiology ──▶ organism equations
                                                        │
  six hardware modules ──▶ static layers ──┐             │
                                           ▼             ▼
                              one opaque composed base   organism raster
                                           └──────┬──────┘
                                                  ▼
                                      dirty-region composition
                                                  ▼
                              cairo ──▶ shared-memory buffer ──▶ compositor
```

The renderer knows nothing about windows. It produces a frame in logical
coordinates; a `FramePresenter` — three methods, no framework — puts it on a
screen. That seam is why the same instrument runs unchanged on two hosts: this
one, and a GTK4 build kept as a reference oracle.

There is no GPU in the path. Cairo composes straight into the compositor's
shared-memory buffer, so a frame is copied exactly once — by softbuffer, when
it hands the buffer over.

Three scales are in play, and confusing any two of them is a whole bug class:
the window's scale factor, the quantised cache scale every cached surface is
rendered at, and the target's exact per-axis device scale. They are reconciled
in one function, gated at six scales.

**Read next:** [`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md) for the resize
contract and the composition model.

## Performance

781×468 logical on a 1.6-scale display (1250×749 device), INSTRUMENT, one
core. The other two columns are the same renderer, on the same machine.

| | Python + GTK4 | Rust + GTK4 | **Somacline** |
|---|---:|---:|---:|
| PSS | 222.0 MB | 184.9 MB | **42.2 – 45.6 MB** |
| RSS | 238.4 MB | 194.7 MB | **53.7 – 56.8 MB** |
| CPU, focused | 21.2 % | 17.5 % | **14.8 – 16.3 %** |
| CPU, unfocused | 13.3 % | 10.7 % | **9.5 – 12.3 %** |
| CPU, off-workspace | 1.3 % | 0.50 % | **0.12 %** |
| threads | 26 | 11 | **2** |
| shared objects | — | 113 | **40** |
| startup to mapped window | — | 0.51 s | **0.21 s** |

GTK composited two full-window layers on the GPU, outside the process, for
free. Somacline does that work on the CPU and still uses less of it — because
it stopped doing most of it. The static picture is composed once; a frame
repaints the glass and whatever region actually changed, measured at 15.8 % of
the buffer.

Every one of those optimisations is gated by a byte-for-byte comparison
against a frame composed the straightforward way. None of them is allowed to
be an approximation. The full account is in
[`docs/rust-migration/OPTIMIZATION.md`](docs/rust-migration/OPTIMIZATION.md)
and the release verification is in
[`docs/RELEASE-VERIFICATION.md`](docs/RELEASE-VERIFICATION.md).

## Installation

Needs cairo, pango and fontconfig — which a desktop Linux system already has —
and a Rust toolchain to build. Developed and verified on Wayland (Hyprland);
winit's X11 backend is compiled in but untested here.

```sh
git clone https://github.com/Ozymandes/SOMACLINE
cd somacline
./install.sh
```

That builds the release binary and installs `somacline` into `~/.local`, with
a desktop entry and icons.

```sh
./install.sh --prefix /usr/local              # system-wide
./install.sh --uninstall                      # removes what it installed
DESTDIR=/tmp/pkg ./install.sh --prefix /usr   # stage for a package
```

On Arch and derivatives:

```sh
sudo pacman -S --needed cairo pango fontconfig
```

To run from a checkout without installing anything:

```sh
./run-somacline.sh
```

### Optional typography

**Somacline ships no font files.** Its typography is designed around two
third-party faces that this project has no right to redistribute, so they are
not in the repository and not in any release.

Without them the instrument runs perfectly well on fontconfig's substitutions
— the layout is metric-driven, so everything composes correctly, it just is
not wearing its own type. If you want the intended look, install either or
both yourself:

| family | role | where to look |
|---|---|---|
| **Microgramma** | technical type: labels, rails, microcopy | <https://online-fonts.com/fonts/microgramma> |
| **Astro** | hero type: major titles | <https://www.dafont.com/astro.font> |

Install from a source and under a licence appropriate to your own use.
Microgramma is a commercial typeface; that link is a place to find it, not a
statement about its licensing for you. The DaFont page for Astro currently
lists it as 100% free.

Either put the `.ttf` files wherever fontconfig already looks
(`~/.local/share/fonts/`), or drop them into `assets/fonts/` in a checkout and
Somacline will register them for you on next launch.

## Linux, Wayland, Hyprland

Somacline is a Wayland-native application. It draws with cairo into the
compositor's shared-memory buffer through softbuffer — **no GPU, no OpenGL, no
Vulkan, no GTK**, and no GPU driver loaded into the process. Forty shared
objects, two threads.

It was developed and verified on **Hyprland 0.56.2** under Omarchy, at display
scale 1.6, including fractional scaling, tiling, floating, fullscreen and
workspace transitions. winit's X11 backend is compiled in but is untested
here.

The frame loop is driven by the compositor's own frame callbacks rather than a
timer, so the instrument never runs ahead of the display — and when a surface
stops receiving callbacks, because it is covered or on another workspace, the
simulation stops with it. That is where the 0.12 % figure comes from. On
resume, elapsed time is clamped so nothing teleports.

**A note for Omarchy users.** Omarchy applies a default window opacity to
every window. Against a near-black instrument the wallpaper shows faintly
through — that is the desktop's setting, not this application. To make it
fully opaque, add to your Hyprland config:

```lua
o.window("dev.somacline.Somacline", { tag = "-default-opacity", opacity = "1 1" })
```

somacline                              # 900x700

somacline --specimen 2                 # open on a specimen (0-4)
somacline --debug                      # with the diagnostic overlay

## How it was made

The question at the top of this file is the honest origin. The escalation
that followed went roughly: the equations, verbatim; then telemetry to drive
them; then a physiology layer so each channel meant something different to
each specimen; then a fictional instrument to put them in; then six generated
hardware modules for the instrument to be made of. A Qt6 prototype came first
and kept falling over in its scene graph, which taught me what I actually
wanted — no GPU state anywhere — so the real base became Python + GTK4, then
a Rust port, then the port got a window host of its own. Somewhere in there
the system monitor had acquired a taxonomy, catalogue numbers and a
calibration overlay. By then, stopping would have been the reckless option.

Around the same time I was reading Bruce Sterling's Shaper–Mechanist stories
— engineered organisms, distributed intelligence, scientific machinery with a
retro-futurist accent — and unable to leave yuruyurau's sketches alone. What
surprised me was not the aesthetic escalation but the engineering one: the
further the visual side went, the more discipline the implementation
demanded, not less.

The instrument was built against two fixed references — a target image and a
module map. The hardware was generated against them, then cut into a
nine-sliceable sprite set by `tools/build_sprites.py`; the generation log,
every prompt and setting and reference, is in `assets/modules/GENERATIONS.md`
— including the four attempts the selector module needed, two of which were
rejected for being geometrically wrong in pixels. An asset you cannot
reproduce is an asset you do not really have, so the ledger records the
model, the settings, the budget and every verdict.

It was written twice. A Python + GTK4 implementation came first and still
lives in `abyssal/`. It is not a second product — it is the **parity oracle**.
The Rust port is diffed against it at six size, scale and layout fixtures, and
the only region that exceeds tolerance is the header clock, which is wall
time. Two runs of the oracle itself differ there by more.

That oracle is why the optimisation could be aggressive. Once a frame can be
*proved* byte-identical to a frame drawn the obvious way, the obvious way
stops being the only safe one. Dirty-region composition, a residency policy
that hands 21 MB of sprite masters back four seconds after you stop
interacting, caches scoped to the live window size — each one landed with a
gate that fails if it changes a single byte of output.

This was also a deliberate experiment in AI-native development — not
autocomplete with extra steps, but AI as the design and production medium:
concept work, visual identity, the industrial design of the hardware,
iterative image generation against the fixed references, decomposition of the
output into sprites, and then ordinary engineering stacked on top —
implementation, visual parity, debugging, profiling, verification. The result
worth reporting is that the visual ambition never relaxed the engineering; it
tightened it. An interface that specific cannot be maintained by eye or by
vibe, so it demanded measurable parity, asset provenance, deterministic
rendering decisions and byte-for-byte gates, and it got them. I will write
the workflow up separately; the short version is that the model drew the
hardware and the harness kept it honest.

`docs/ASSETS.md` records what ships and what is design source.
[`CHANGELOG.md`](CHANGELOG.md) records the release.
